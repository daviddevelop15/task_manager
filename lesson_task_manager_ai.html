Inside the Task Manager App & Its AI Engine

A 10–15 minute technical lesson: how a real PyQt6 desktop app is built, how it protects your data, and how it uses Large Language Models (Claude & GPT) to help you land a job.

1. What is this app? ~1 min

The Task Manager is a Windows desktop application for tracking work — especially a job-application workflow. It is organised into five tabs:

Tasks

Track links/URLs with a status workflow and multiline notes.

Daily

An Excel-style multi-sheet grid of daily cards — where the AI lives.

Meetings

A month-grid calendar with repeating alarms & pop-ups.

Sticky notes

Free-form quick notes.

Acc

Encrypted account/password store.

Open the app and click through the five tabs. Point out that everything is stored locally on the machine — there is no server. This one design choice drives both the security work and the threading work we'll see later.

2. Architecture & tech stack ~2 min

The whole app is built from a handful of well-known, dependable technologies. Only three external packages are required:

# requirements.txt
PyQt6>=6.6.0        # the GUI framework (windows, tables, dialogs)
cryptography>=42    # AES-256-GCM, scrypt — the encryption primitives
anthropic>=0.69     # official Claude SDK (OpenAI uses no extra package)

Separation of concerns (one job per file)

Teaching point — layering: the UI never talks to Claude directly. The screen (daily_sheet_page.py) calls a plain Python function in ai_assistant.py, which is the only file that knows about AI providers. Swap the AI vendor and the UI never changes. This is the single-responsibility principle in the wild.

3. Data security: encryption at rest ~2 min

Because the data (job details, passwords, résumés) lives in a local file, the app encrypts it. The design is called envelope encryption:

Your password
or Windows login
→
unwraps a
Key-Encryption-Key
→
which unwraps the
Data-Encryption-Key (DEK)
→
which decrypts the
whole database
  • One random 32-byte key (the DEK) encrypts all data with AES-256-GCM.
  • That key is "wrapped" (locked in an envelope) two interchangeable ways:
    • DPAPI mode no password — Windows unlocks it silently for your user account.
    • Password mode a password you type is stretched with scrypt into the wrapping key.
  • Changing your password only re-wraps the envelope — the huge database is never re-encrypted. Fast and safe.
  • Plaintext data only ever exists in RAM (an in-memory SQLite database). Changes are flushed to the encrypted file with a 0.8-second debounce so a burst of edits becomes a single write.
Engineering trade-off worth teaching: the debounced flush means a hard crash could lose up to ~0.8 s of edits — accepted deliberately because the old "save on every edit" approach re-encrypted the entire file dozens of times during a single drag-and-drop and made the app feel slow. Good engineering is choosing which trade-off to make, on purpose.

4. The AI feature in action ~2 min

On a Daily card (representing one job you're applying to) the AI assistant offers four things, all grounded in your résumé and the job description:

📊 Match score

A 0–100 fit score with concrete strengths and gaps.

✍️ Answer a question

Drafts a first-person answer to an application question.

📄 Cover letter

A tailored 3–4 paragraph letter.

🔎 Parse a posting

Pastes raw job text → clean Company/Role/Location/URL fields.

Your résumé is stored (encrypted) in the app — even as a PDF. When you upload a PDF, it's sent to Claude directly as a document, no manual copy-paste needed.

If a demo is possible: paste a job description into a card, pick a résumé, click "Check match score", and show the score + strengths/gaps appearing. This is the "wow" moment — then the next section explains what happened behind that click.

5. How the AI actually works ~3 min

This is the heart of the lesson. An LLM (Large Language Model) like Claude or GPT is a text-in / text-out engine. The app's job is to (1) build a good prompt, (2) send it over the internet to the model, and (3) parse what comes back.

Provider-switchable design

# ai_assistant.py — one function, two back ends
def _complete(system, max_tokens, tail_text, resume_text=None, resume_pdf=None):
    if ai_provider() == "openai":
        # Chat Completions over stdlib HTTP — no extra dependency
        return _openai_complete(system, user_text, max_tokens)
    # Anthropic: build "content blocks" (text, or a PDF document block)
    content = _resume_blocks(resume_text, resume_pdf)
    content.append({"type": "text", "text": tail_text})
    return _anthropic_complete(system, content, max_tokens)

The two building blocks of every LLM call

PartWhat it isExample in this app
System promptFixed instructions that set the model's role & rules."You are an expert technical recruiter… respond with ONLY a JSON object…"
User messageThe actual data for this request.The résumé (as text or PDF) + the job description.

Sending a PDF to Claude (content blocks)

Instead of one string, Claude accepts a list of typed blocks. A PDF is base64-encoded into a document block — the model reads the PDF itself:

[
  {"type": "text", "text": "=== CANDIDATE RESUME (attached PDF) ==="},
  {"type": "document",
   "source": {"type": "base64",
              "media_type": "application/pdf",
              "data": "<base64 of the PDF>"}}
]
Vendor difference to note: OpenAI's chat endpoint here takes plain text, so the app extracts the PDF's text first. Same feature, two implementations — hidden behind the same function.

6. Prompt engineering & structured output ~2 min

An LLM naturally replies in prose. But software needs predictable data. The trick is to ask for JSON in the system prompt, then parse it. This is the match-score prompt:

"You are an expert technical recruiter and career coach. Assess how
 well the candidate's resume matches the job description... Respond
 with ONLY a JSON object (no markdown, no prose) of the form:
 {\"score\": <0-100>, \"summary\": \"...\",
  \"strengths\": [\"...\"], \"gaps\": [\"...\"]}"

The reply is then turned into a real Python object — defensively, because models sometimes wrap JSON in extra text:

def _extract_json(text):
    try:
        return json.loads(text)          # happy path
    except ValueError:
        pass
    m = re.search(r"\{.*\}", text, re.DOTALL)  # find first {...} block
    if m: return json.loads(m.group(0))
    raise ValueError("The model did not return a parseable result.")

Guard-rails baked into the prompts

  • No hallucination: "Do not invent facts, employers, or credentials not in the resume."
  • Clean output: "Use only plain ASCII punctuation" — then a normalize_punctuation() pass still swaps any smart-quotes/em-dashes for keyboard characters (belt and braces).
  • Language & length control: answers can be forced into English, Spanish, both, or a character limit.
  • Input trimming: résumé/job text is clipped to ~24k characters so prompts stay within the model's context window and costs stay bounded.
Big idea: "AI in an app" is 20% calling the model and 80% engineering around it — prompting precisely, constraining output, validating results, and handling every way it can go wrong.

7. Keeping the UI responsive: threads ~1 min

An AI call takes several seconds. If it ran on the main thread, the whole window would freeze. The app runs it on a background worker thread and reports back with a signal:

class AIWorker(QObject):
    finished = pyqtSignal(object, str)   # (result, error_message)

    def run(self):
        try:
            result = self._fn()               # the AI call, off the UI thread
            self.finished.emit(result, "")
        except Exception as exc:
            self.finished.emit(None, format_error(exc))  # friendly message

Errors are translated into plain English (format_error): a bad key → "Invalid API key. Check it in Settings", a rate-limit → "Try again shortly." The user never sees a raw stack trace.

8. Key takeaways & discussion ~1 min

Layer your code

UI, data, and AI are separate files. Each can change without breaking the others.

Security is a design, not a bolt-on

Envelope encryption + in-RAM plaintext + debounced writes.

LLMs are text engines

System prompt (rules) + user message (data) → text back.

Constrain the AI

Demand JSON, forbid hallucination, validate everything it returns.

Never freeze the UI

Long network calls belong on a worker thread.

Design for failure

Every API error becomes a clear, human message.

Discussion questions for the class

Why does the app send a résumé + job description on every request instead of "training" the model on your data?

Because these hosted LLMs are pre-trained and used via prompting (in-context learning), not fine-tuning. You supply the relevant facts each call. It's cheaper, instant, private per-request, and keeps the model general.

What could go wrong if we trusted the model to always return valid JSON?

It might wrap JSON in prose, add markdown fences, or miss a field. That would crash a naive json.loads. Hence the defensive _extract_json regex fallback and the clamping of score to 0–100.

Why encrypt in memory and flush after 0.8s rather than saving on every keystroke?

Re-encrypting the entire file on every edit was slow. Debouncing coalesces a burst of edits into one write. The cost is losing at most ~0.8s of work in a hard crash — an accepted, documented trade-off.

How does the "provider-switchable" design help the business?

No vendor lock-in: if one provider is down, too expensive, or a better model appears, you flip a setting. The UI and features are untouched because everything funnels through _complete().
